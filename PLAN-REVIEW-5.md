# UX Plan Review — Round 5

**Verdict.** v4.1 is executable in substance and eroded in form. The five CX4-era mechanisms this round source-checked mostly hold — better than any prior round's inventions: the idempotency middleware has a natural single insertion point, the TEXT widening has an exact one-file precedent, the root-event association has an atomic home in the existing unit-of-work, and the scale dataset has a carrier the plan doesn't know it owns (the export path already emits a portable SQLite file). Only the K8a `result.json` envelope needs respec — it invents a third producer channel while the put path already parses a structured stdout result and K3's `{version, metadata}` split lands in the same phase. But eight rounds of surgical patching have left the document a palimpsest: the intro still describes the pre-R4-1 run model that §2.1 replaced; "push-at-put" survives in two places after K8's rewrite reassigned it; §7 and §8 flatly contradict each other on the scale generator; K9's implementation lands in no phase; acceptance targets ("A3/A4/A5 targets", "ideal #8/#9") point at a v3 journeys table and an ideals list that exist nowhere in the corpus; and three K-cells are 200–300-word essays interleaving three phases each. **Is the patched state better or worse than a clean rewrite?** Better — decisively. The error history shows rewriting is where this corpus mints new defects (every round's worst findings were freshly invented mechanisms; the patches that merely corrected text almost always held), and v4.1's load-bearing structure — K-table with lands/fallbacks, spike list, cut lines — is sound. What it needs is not a v5 but a copy-edit commit (the scar list below, mechanical, no design decisions) plus one extraction: a self-contained PHASE-0.md, because the one document a new contributor must execute first is currently the one most dependent on the ghost of v3.

### R5-3. [SEV-2] K8a's `result.json` producer envelope invents a third channel: put steps already return a structured result on stdout, and K3's metadata envelope lands in the same phase
**Where:** K8 row ("a put step may write `result.json` … to a declared output path; builtin types emit it" — CX4-5); source: `worker/service.go` `runPutStep`/`implicitGetAfterPut`, `builtin/resource_types/artifact.hcl`.
**Problem (source):** The put protocol already has a result channel: the **last stdout line** of the push script is parsed as a JSON version array (`implicitGetAfterPut`), each entry inserted via `CreateResourceVersion`, recorded on the step (`VersionID`) and in `build_get_versions` — the artifact type's `echo "[{\"sha\":…,\"timestamp\":…}]"` is exactly this. Today that channel's content is *identity* (the K3 problem — manifests can't go there raw). But K3 (same phase as K8a, Ph2) redefines check output as `{version, metadata}` with bare-map back-compat; the symmetric move is to extend the *same envelope to push output* — last line becomes `[{version: {...}, metadata: {files, destination}}]`, parsed by the code that already parses this line, metadata stored via the channel K3 builds. The `result.json`-file design instead requires: a declared-output-path convention, the worker knowing the path per put step, reading the file post-script, and new plumbing to ship it — none of which exists — while creating two different producer protocols (stdout for versions, file for results) that every custom resource type author must learn. CX4-5's fallback ("output metadata unavailable") is right and survives either design.
**Fix:** Respec CX4-5's envelope to ride the existing stdout channel under K3's `{version, metadata}` shape (one parser, one protocol, one back-compat rule); keep `result.json` only if a put's metadata can exceed sane stdout size — and say which. One paragraph in K8; the K3 design memo (§10.6) should ratify both directions of the envelope at once.

### R5-4. [SEV-3] K9's implementation lands in no phase: the K-table says Ph1a, §7's deliverable lists never mention it, and §4 builds "liveness" on it
**Where:** K9 row ("decide Ph0 · land Ph1a"); §7 Phase 0 ("Ratify: … K9"), Phase 1a and 1b deliverable lists (absent from both); §4 ("liveness via K9"); §3.11 ("transport decision (K9)").

A Ph1a that ships the build page v2 and follow-mode without the transport landing quietly inherits today's polling (which the mainline is actively firefighting — CHANGELOG #652's 16MB/50-build responses and the 0.7.0 polling-CPU fixes are the live pain). **Fix:** Add "K9 transport lands" to Phase 1a's deliverables (it belongs there — see pre-mortem) or move the lands cell to Ph1b and say the 1a build page runs on today's polling, stated.

### R5-5. [SEV-3] The checked-in scale dataset has a real carrier the plan doesn't name — the SQLite export — and one missing 10-line flag
**Where:** §8 ("a checked-in static scale dataset (generated once, committed: ~100 pipelines, one 30-job fan-out)"); source: `pikoci/transport/http/export.go`, `docs/CLI.md` (`pikoci client export -o backup.db` — "portable SQLite file"), `cmd/server.go` (sqlite path hardcoded to the XDG data file; no `--db-file` flag).
**Problem (source):** The plan names the artifact but no mechanism, which in past rounds is where inventions crept in. None is needed: the export path already produces a full-DB portable SQLite file, the server runs on `--db-system sqlite`, and the startup migrator upgrades an old-schema file automatically — so the fixture is "a committed `.db`, generated once by a script driving the real API, restored before the Ph1b exit run." The one gap: the sqlite path is hardcoded (`~/.local/share/pikoci/pikoci.db`), so "restore" is a copy-into-place today; a `--db-file` flag is ~10 lines and makes the fixture a one-command harness. Without naming this, an implementer may build a dev-mode data loader (fake-data seeding) — a parallel mechanism with drift risk against real schema.
**Fix:** One sentence in §8: dataset = committed SQLite export, restored via `--db-file` (small enabler flag, add to Ph1b deliverables); generation script checked in beside it.

## Mechanism checks (CX4-era patches vs source)

| Mechanism | Verdict | Evidence |
|---|---|---|
| K8a `result.json` producer envelope (CX4-5) | **needs respec — partially redundant** | Put output already IS a parsed result channel: last stdout line → JSON version array → `implicitGetAfterPut` → `CreateResourceVersion` + step `VersionID` + `build_get_versions`. The envelope should ride this channel under K3's `{version, metadata}` split (same phase), not a new declared-path file convention with unbuilt worker plumbing (R5-3). |
| K18-minimal idempotency keys in Ph1a (CX4-3) | **holds** | All mutating routes live on one gorilla/mux subrouter with **named routes** (`RetryJobBuild`, `CancelJobBuild`, `ApproveBuild`…) behind a single `api.Use(auth)` chain, and every handler funnels through one `encodeResponse` (uniform 200/400 + Errorer JSON). A second middleware — route-name allowlist + `Idempotency-Key` + response-capturing writer + one key table — is a genuine single insertion point; no per-handler surgery. Cost honestly: the key table is a new stored record needing a retention class like the others. |
| MySQL TEXT→wider migration (CX4-4 prerequisite) | **holds — genuinely small** | Exact precedent exists: `V30WebhookTokenLength.go` is a one-file `ALTER TABLE … MODIFY COLUMN` widening. `adaptSQL` already strips MODIFY COLUMN for SQLite/mem (no cap there anyway) and rewrites it to `ALTER COLUMN … TYPE` for Postgres; a `LONGTEXT` widening needs one added replace line in the Postgres branch (`LONGTEXT`→`TEXT` — no mapping exists today, grep-verified). One note for the migration text: MODIFY on a large `builds` table is a table rewrite — flag the upgrade duration for big MySQL installs. |
| Root-event→root-build association (CX4-1) | **holds** | Every build-creation path (check-trigger loop, manual trigger, implicit-get-after-put) funnels through `CreateJobBuild`, whose insert runs inside `StartUoW` — a `root_event_id` on the build row is written atomically with the build by construction; for manual triggers the root-event row itself can be minted inside the same UoW closure. Bonus: `triggerResourceJobs` creates root builds *unconditionally* per new version (no pending-coalescing at the root — that guard is downstream-only), so root events map 1:1 to root builds, which is exactly what CX4-1's double-trigger disambiguation needs. |
| Checked-in static scale dataset (CX4-6) | **holds, mechanism unnamed** | No seed/fixture loader exists — but none is needed: `GET /admin/export` / `pikoci client export` emits a portable SQLite DB, `--db-system sqlite` consumes one, and the startup migrator upgrades old-schema fixtures automatically. Missing: the sqlite file path is hardcoded to XDG (no `--db-file` flag), so restore is copy-into-place (R5-5). |

Score: 4 hold / 1 needs-respec — the best mechanism-survival rate of any round, and the first round where the *newest* patches were the soundest. The invention-without-source-contact failure mode is genuinely fading.

## Pre-mortem — Phase 1a ships as specified, and lands flat

**Cause 1 — it ships diagnosis depth where the felt pain is latency and liveness.** The Unreleased CHANGELOG is a confession of what actually hurts daily: 16MB build-list responses, 6–8s pipeline images, polling CPU storms, stale build tabs, missing elapsed timers, and forge-status *immediacy* — so acute the team built `on_trigger` (#528) themselves rather than wait for the plan's Ph1b notify item. Phase 1a's flagship (error-first page, inline non-run reasons, compare-with-last-green) improves the *bad* days; the audience's *every* day is dominated by waiting for signal, and 1a doesn't move that — K9's transport implementation isn't even in the phase's deliverable list (R5-4). The team will use 1a's features and feel nothing change in the loop they run forty times a day.

**Cause 2 — the flagship surfaces have almost no traffic on the real config.** The dogfood has no approval gate (the context bar renders empty until the dogfood-track gate lands, and "Ph1" doesn't say when — R5-1.9), few `passed`-chains and no fork-hold traffic from its own team, and the biggest silent-non-run generator was just fixed in mainline as an ordinary bug (#656's infinite trigger loop). Inline reasons will mostly display reasons nobody was confused about; the attention strip's three classes will be near-empty; and per-session-only dismissal (no snooze until 1b) means any class that *does* fire nags. A canary that stays silent because it's unfed is indistinguishable from one that works — and reads as "nothing shipped."

**Cause 3 — the audience's front door is the forge, and Phase 1a doesn't touch it — while Phase 0 makes it slightly worse first.** OSS users and the dogfood team alike enter through GitHub PR checks, not Home; the community's shipped demand (#528, #467, #164, #612) clusters on forge immediacy and pipeline-authoring control. The plan's forge-visible wins (held-fork status, the `on_trigger` port that fixes two live bugs) sit in Ph1b behind the queue-table subsystem — and the first thing the community actually experiences is Phase 0's fork-hold with a CLI-only release valve and no strip item (R5-1.8). First contact with the initiative is friction; the payoff surface arrives two phases later, somewhere they don't look.

**Swap recommendation.** One out, two in, one binding: (out) **K20-CAS → Ph1b** — the config-edit race is real but rare and invisible to solo/dogfood use; (in) **K9 transport actually lands in 1a** (this is also just fixing R5-4's drift honestly — liveness is the single most-repaired pain in the product's own changelog); (in) **promote the `on_trigger`→notify-work-item port from "spike 3's first deliverable" to a shipped Ph1a item** — the spike builds it anyway, it fixes two filed security/correctness bugs, and it is the one Phase-1a-sized deliverable the community has already demonstrated demand for by building its broken version themselves; (binding) the dogfood approval gate lands at **Ph1a start**, stated as the precondition of the context-bar exit criterion.

## Cold-reader assessment

Could a new contributor execute Phase 0 from UX-PLAN.md alone? **No.** Top three failures:

1. **Unresolvable acceptance targets.** Phase exits cite "A3/A4/A5/B11 targets", "B1 diff-arm", "ideal-#8/#9 scripts" — the journey table defining the targets is v3's (not in the corpus, R5-2) and the ideals list was never carried past v2 (R5-1.7). The executor cannot know what "pass" means.
2. **K1-minimal is never defined.** The K-table says "min Ph0 · full Ph1a" with no split stated; the contributor must reverse-engineer it from the Phase-0 exit line ("intent inputs + config rev recorded") plus a parenthetical in §10.0 ("keep the full `candidates` list… this is also K1-minimal's intent data"). Whether worker identity or run links are in the minimal slice is a coin flip.
3. **K7-crude's Phase-0 subset must be excavated from a 300-word three-phase cell plus four other locations** (§2.1's fork bullet, §10.1's acceptance, the Phase-0 exit, §6's H1 note), and Phase 0's internal ordering — K2 spike before K2 ratification, K3 design ratification before the K7 dedup slice it constrains — is implied by cross-references, never stated as a sequence.

**Yes — extract a PHASE-0.md brief.** Outline (not written):
1. Goal sentence + the Phase-0 exit criteria verbatim.
2. File-first: the four today-bugs (from §10).
3. Sequence: K2 spike → K5 prototype → K3 design ratification → K7 spike → K7-crude implementation; K19 spike + backend/retention memo in parallel.
4. Decisions to ratify, each one page: K2 (post-spike), K3 design, K9, memo.
5. K1-minimal, defined: all candidate inputs at creation + config-rev id + root-event association (per §2.1); explicitly *excluded*: execution-time resolution, worker identity (Ph1a).
6. K17: pause/pin actor/reason/expiry schema; solo prefill rule.
7. K20a: append-only config history — no CAS, no restore, no UI.
8. K7-crude, the Ph0-only extract: fork side column + `{ref,pr}`-projection dedup; hold derived at every creation path; the five dispatch exclusions; `pr_hold` strictly parsed; release verb API + CLI.
9. Acceptance tests verbatim from §10.1 (zero-re-mint upgrade, held retry/trigger-with-version, CLI release, dispatch under a queued non-fork PR) + §10.0's cases including double-trigger.
10. Non-goals: no UI, no forge reporting, no K3 metadata channel, no strip.

## Closing

The corpus is done, and this round is the evidence: five of five prior-round mechanisms survived source contact or needed only a one-paragraph respec, the finding stream has decayed from "the backend doesn't work that way" (round 1) through "the protocol can't carry that" (round 3) to "two patches disagree about a word" (this round) — copy-editing defects, which are real but are not what review rounds are for. I found no source-checked SEV-1, which by the plan's own §10 stopping rule means no v5; I see no reason to override that rule and several to enforce it, since the one defect class still being produced (patch scars) is *caused by* review-driven patching. Stopping rule, concretely: apply R5-1's fourteen edits and R5-3/R5-4/R5-5's paragraph-sized respecs as a single silent v4.2 commit with no review pass; inline the §6 journeys table and extract PHASE-0.md (both are transcription, not design); then freeze the document and run the six spikes. The next legitimate reviewer of this plan is a failing spike acceptance test or the Phase-1a exit demo — and the pre-mortem above suggests the most valuable thing anyone can do before then is not read this document again but re-order Phase 1a around the latency-and-forge pain its own changelog keeps confessing.
